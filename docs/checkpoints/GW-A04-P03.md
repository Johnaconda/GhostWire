## Demonstrated defect and repair

A profile can explicitly pin and accept its own membership's public DeviceSet.
After local device revocation, recognition intersects that older accepted set
with the latest owned membership record and correctly rejects the device.
P02 `delete_membership` removed the owned record but left its matching self-pin.
Recognition then fell back to the older accepted set and could recognize the
revoked device again through the existing trust handle.

P03 invalidates exact-authority self-trust slots in the deleting profile before
removing the owned membership. Existing generation-safe erasure invalidates
stale capabilities and releases retained trust/frame accounting. Cancellation
and deadline checks precede the bounded, allocation-free commit. Other authority
contexts and other profiles remain unchanged. A future explicit re-pin is a
new local trust decision, not revival of the deleted capability.

The added regression reproduced the P02 failure: **1 case failed** at recognition
after deletion, 36/37 assertions passed. With the fix: **1 case / 58 assertions
passed**. The targeted filter deliberately excluded 40 unrelated cases; the
full-suite runs below cover them. The regression also checks cancelled deletion,
invalidated membership/trust handles, released key/trust/frame budgets, unrelated
trust, observer-profile independence and a fresh empty re-pin.

Two parallel assistant reviewers inspected the service and record/CLI/composition
surfaces. A second reviewer independently checked this fix. No additional concrete
blocking issue was found in that bounded review. This is not an external security
audit or a claim of exhaustive verification. The parser's canonical frame rules,
CLI command set, provider, dependency graph and lifecycle architecture are unchanged.
`forget_community` retains the membership/owned record; profile deletion and close
clear their containing trust state, so those removal paths do not lose this guard.

## Security and limitations

A11-PRE and AUTH-PRE are unchanged. No private-key/profile/trust persistence,
networking, listener, remote enrollment, login protocol, GUI, AI or future-checkpoint
functionality was introduced. Keys and trust are still volatile. Signature
validity and local device recognition are not live possession, community admission
or action permission. Root recovery/continuity remain deferred.

This repair prevents stale self-trust revival in the owning profile. It does not
broadcast revocation to other independent profiles or remote parties and does not
persist a blacklist after explicit forgetting. Other profiles require their own
explicit record acceptance or trust changes. There are no new private files,
backup/cache/index formats or diagnostic disclosures. Existing process-memory,
swap/crash-dump, cooperative-deadline, logical resource-budget and synchronous
stdin limitations remain as documented in P02. No production E2EE claim.
